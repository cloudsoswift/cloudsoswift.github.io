발단

nginx에서 upstream을 컨테이너 이름으로 지정해 사용하고 있었는데, upstream로 지정됐던 컨테이너들을 새로 만들때마다 502 에러가 발생했다.
이를 고치기 위해 매 번 docker compose nginx restart를 통해 nginx 컨테이너를 재시작하여 새로 생성된 upstream 컨테이너의 최신 주소를 읽도록 했었다.
이러한 오류가 발생했던 이유는, nginx가 upstream의 호스트 이름을 nginx 설정을 읽을 때 딱 한 번만 IP로 바꾸어 기억하기 때문이었다.

1. nginx 기동 → spring 을 조회해 172.18.0.5 를 기억한다.
2. spring 컨테이너를 다시 만든다 → Docker가 새 IP(예: 172.18.0.9)를 준다.
3. nginx 는 여전히 172.18.0.5 로 보낸다 → 아무도 없으니 연결 실패, 502.
4. nginx -s reload → 설정을 다시 읽으며 이름을 다시 조회해서야 복구된다.

- nginx, spring, nextjs 컨테이너는 모두 같은 docker compose의 브리지 네트워크에 존재한다.

이러한 갱신을 일종의 자동화를 시키기 위해, resolver 및 resolve 키워드를 사용하게 됐다.

resolver는 무엇인가?

resolver 는 nginx가 실행 중에 도메인 이름을 물어볼 DNS 서버를 지정하는 지시어다. 이러한 네임 서버는 업스트림 서버의 이름을 주소로 변환하는 데에 사용된다.

resolver 127.0.0.11 valid=10s ipv6=off;

upstream server_name {
    zone server_name 64k;   # resolve 는 워커들이 공유하는 메모리 영역이 필요하다
    server ${ip} resolve;
  • resolver 127.0.0.11
    • 질의할 DNS 서버. 127.0.0.11는 Docker가 사용자 정의 네트워크의 모든 컨테이너 안에 만들어두는 내장 DNS로, 컨테이너 이름을 현재 IP로 바꿔 준다.
  • valid=${time}
    • 조회한 결과가 얼마나 유효할지
  • upstream server ... resolve
    • resolve는 이 서버의 이름을 주기적으로 다시 조회하라는 표시다. 없으면 resolver가 있어도 nginx 컨테이너 기동시 한 번만 조회한다.
  • upstream zone
    • 여러 워커 프로세스가 함께 보는 공유 메모리. 새로 찾은 IP를 워커 전체에 알리는 공간이므로 resolve를 쓰려면 반드시 필요하다.

resolver를 사용하면, upstream의 IP가 바뀔 수 있는 환경에서 nginx가 알아서 따라가게 할 수있다.
Docker 컨테이너, 쿠버네티스 서비스, 클라우드 로드밸런서처럼 주소가 고정되지 않은 대상이 전형적인 예다.

이 기능은 원래 유료 버전인 NGINX Plus 전용 기능이었으나, 오픈소스버전 nginx에는 1.27.3부터 들어왔다.
버전 별 변경사항 문서
Dynamic DNS Resolution Open Sourced in NGINX - NGINX Community Blog
이 기능이 들어오기 전까진 proxy_pass http://$변수;와 같이 변수를 써서 요청마다 조회하게 만드는 우회법을 썼다. (다만, upstream을 쓸 수 없는 방법이라 keepalive 연결 재사용과 같은 이점을 포기해야 했다.)

사용법 

# nginx.conf

# 컨테이너 이름(spring, next)을 Docker 내장 DNS 로 주기적으로 다시 조회한다.
resolver 127.0.0.11 valid=10s ipv6=off;

upstream spring_backend {
    zone spring_backend 64k;   # resolve 는 워커들이 공유하는 메모리 영역이 필요하다
    server spring:8080 resolve;
    keepalive 64;
    keepalive_requests 10000;
    keepalive_timeout 60s;
}

upstream next_frontend {
    zone next_frontend 64k;
    server next:3000 resolve;
    keepalive 32;
    keepalive_requests 10000;
    keepalive_timeout 60s;
}
  • resolver 127.0.0.11: Docker 내장 DNS. nginx.conf 파일 최상단(http 컨텍스트)에 두어 두 upstream이 함께 쓴다.
  • valid=10s: 컨테이너의 새 IP를 nginx가 알기까지 최대 10초. Spring 컨테이너는 뜨는 데 그보다 오래 걸리므로 실제로는 체감할 수 없다.
  • ipv6=off: 브리지 네트워크가 IPv4만 쓰므로 AAAA 조회를 하지 않는다.
  • zone <이름> 64k: upstream마다 64KB 공유 메모리.(server 한 줄짜리 upstream에는 충분하다.)
  • server spring:8080 resolve: 이 upstream 이름을 resolver로 계속 다시 조회하라는 표시.

추가적으로, docker-compose.yml에 nginx 1.27.3이상 버전의 이미지를 쓰도록 기입해두었다.

실제 동작

resolver가 제대로 동작하는지 검증하기 위해 간단한 테스트를 진행했다.
upstream을 사용하는 컨테이너의 IP가 바뀌도록 하고, nginx reload없이 이후 요청이 새 컨테이너에 도달하는지 확인하는 것이다.

1. 바꾸기 전 IP 기록 

$ docker network ls | grep app-net # 네트워크 이름 확인
150aeebbb648   podor_app-net   bridge    local
$ docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' home-spring # spring 컨테이너의 ip 확인
172.18.0.5

2. IP 가 바뀌도록 컨테이너 재생성 

$ docker compose rm -sf spring # 컨테이너 삭제. s: 컨테이너 중지, f: 강제 삭제
$ docker run -d --rm --name ipgrab --network podor_app-net alpine sleep 600 # alpine 이미지 기반 컨테이너 만든 뒤 10분간 슬립
$ docker compose up -d spring # spring 컨테이너 생성 및 실행
$ docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' home-spring # spring 컨테이너 ip 확인 -> 이전과 다른 ip
172.18.0.9

docker compose restart를 사용할 경우, 같은 컨테이너를 단순히 다시 켜서 IP가 그대로일 때가 많다.
그래서 컨테이너를 지우고, 임시 컨테이너(ipgrab)로 같은 네트워크의 IP 하나를 먼저 차지한 뒤 spring 컨테이너를 새로 만들었다.

3. reload 없이 요청 

$ curl -sk -o /dev/null -w '%{http_code}\n' https://localhost/api/events
401 # `Spring Security`가 "로그인 필요" 라고 답한 것으로, 즉 `nginx`가 새 IP의 Spring 컨테이너까지 도달했음을 의미
$ docker compose logs --since 5m nginx | grep -iE "upstream|connect\(\) failed"
(출력 없음) # connect() failed 나 upstream 오류가 한 줄도 없다. 즉, 죽은 IP 로 보낸 요청이 없었다는 뜻이다.

대안 - CI에서 reload를 하는것은?

CI/CD 파이프라인에서 배포 끝에 nginx -s reload를 넣는 방법도 있다. 하지만 그것은 CI로 배포할 때만 막아 준다. 컨테이너가 새로 뜨는 경우는 배포 말고도 있다.
특히 Spring 컨테이너가 메모리 부족으로 죽고 restart: unless-stopped로 다시 뜰 때는 아무도 모르는 사이에 502 가 나게 된다.
그래서 CI를 도입하더라도 resolve는 유지하고, reload는 nginx 설정이 바뀐 배포에만 넣는 구성이 낫다.

resolver 방식의 한계는 두 가지다.

  • valid 초 만큼의 지연 — 새 IP를 알기까지 valid만큼 걸린다. 더 짧게 하면 조회가 잦아지지만, 로컬 DNS라 비용은 여전히 작다.
  • Docker DNS에 의존 — 조회가 실패하면 nginx는 마지막으로 알던 주소를 계속 쓴다.

정리하면, upstream이 컨테이너처럼 주소가 바뀔 수 있는 대상이라면 resolver + zone + resolve 세 가지를 함께 설정해 두는 것이 기본값이다.
